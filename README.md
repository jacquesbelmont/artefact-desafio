# Empório da Música — AI customer support agent

> **Artefact AI Engineer technical challenge.** Educational prototype in Python. The store, orders, and customers belong to the challenge's fictional scenario; this system **is not a production customer support system**.
>
> **Language note:** this README is in English so all submitted material is reviewable in English, as requested by the recruiter. The conversational agent itself naturally replies in **Brazilian Portuguese** (and in an informal-but-professional tone), because the fictional store, its customers, and its policy manual are Brazilian — that is the scenario's language, not a leftover from an untranslated prototype.

## 1. What the project delivers

A text-messaging agent that replies in Brazilian Portuguese, in the informal-yet-professional tone of Empório da Música. The agent distinguishes between when it needs to **query structured data** (products, prices, stock, orders, and promotions), when it needs to **consult policies** (hours, payment, shipping, returns, and warranty), and when it needs to **decline out-of-scope topics**.

Responses are generated by an LLM with *function calling*. Facts come from read-only Python functions; the LLM has no direct access to the filesystem, the terminal, credentials, or financial operations.

### Architecture

```text
Client (CLI)
    |
    v
main.py -> agent.py -> history.py (local SQLite)
               |
               +--> providers.py --> Groq (primary)
               |                 \--> OpenRouter (optional fallback)
               |
               +--> tools.py --> CSVs: products/orders/customers/promotions
               |            \--> policies.py --> policy PDF (pages)
               |
               +--> response in Portuguese + tools used
```

**There is no web API or WhatsApp integration in this prototype**, since the brief allows a CLI. This scope keeps the solution easy to run and evaluate.

## 2. Prerequisites

- macOS, Linux, or Windows with Python **3.11 or higher**.
- Internet access for calls to the language model.
- A **Groq** key for the primary demo, or an **OpenRouter** key to run with only the fallback.
- The fallback API is **optional**; there is no requirement to register a card or spend credits to run the automated tests.

## 3. How to install and run

Run in the terminal, **from the repository root** (`agent/` in the original environment):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
```

Edit the `.env` file and fill in **only** the key you intend to use:

```dotenv
GROQ_API_KEY=your_key_here
GROQ_MODEL=openai/gpt-oss-120b

# Optional: fallback for 429 errors, timeouts, or transient failures
OPENROUTER_API_KEY=
OPENROUTER_MODEL=openai/gpt-4o-mini
LLM_TIMEOUT_SECONDS=25
```

Never publish `.env`, and never put the key in the README or in the code. The file is in `.gitignore`.

Start the support agent:

```bash
python main.py
```

Example questions:

```text
Quais violões vocês têm até R$ 1.000?
Quanto custa o Yamaha C40?
Quais são as formas de pagamento?
Comprei online. Posso devolver?
Qual o status do pedido 2?
Qual a melhor receita de bolo?
```

A new session is assigned an identifier shown in the terminal. To resume a history:

```bash
python main.py --sessao demo-12345678
```

Type `/sair` to exit. The local database lives in `.local/conversas.sqlite3` and **is not versioned**.

## 4. Tests

### Automated tests (no API, no cost)

```bash
python -m pytest -q
```

The suite checks CSV reading, price and stock logic, basic order protection, policy lookup, SQLite history, tool usage, and the Groq-to-fallback switch when an HTTP `429` failure is simulated. It also verifies that an HTTP `400` error is never masked by a fallback retry.

**Checkpoint status:** at the latest verified checkpoint, the offline suite passed **38/38** (independently re-run and confirmed by a reviewing architect pass). This number reflects the offline, mocked-provider suite only — it says nothing about live-model response quality.

### Real-API demonstration (may consume quota/credits)

```bash
python test_atendimento.py
```

To record the 3–5 conversations required by Artefact:

```bash
python test_atendimento.py | tee exemplos/conversas_reais.md
```

**Important:** this file is only real evidence after the command has actually been run and the answers checked manually. The project does not include invented API results. Automated tests with fake models do not demonstrate the quality of the final response.

If Groq rate-limits the requests and a fallback is configured, the agent tries the second API. If no API responds, it reports the problem and keeps the message in history.

**Reproducible diagnostic history:** `exemplos/diagnostico_inicial.md` preserves the original live run exactly as captured (3/4 by the script's basic metric). Its catalog answer incorrectly denied that acoustic guitars under R$ 1,000 were available even though the CSV contained matching products, and its address scenario failed because the provider was unavailable. This is evidence of problems found, not a passing acceptance run.

**Live validation after fixes:** `exemplos/conversas_reais.md` records a later, genuine four-scenario Groq run with **4/4 checks passing**, including actual policy and catalog tool calls. The displayed acoustic guitar products and prices were cross-checked against the CSV. This score is a limited scripted check, **not proof of production readiness or complete factual accuracy**: the return-policy answer still suggests sharing customer details to initiate a return, although this prototype cannot actually open or forward a return request. That requires a real human handoff or further response safeguards.

**Further verification:** the prompt was subsequently refined to direct return requests to human support without collecting personal data for a nonexistent workflow. The revised return-policy scenario passed on its own (1/1, real Groq). In a later four-scenario repetition, the policy case encountered Groq HTTP 429 (Retry-After: 6 seconds), so that later run scored 3/4 because of provider throttling. This is a real availability limitation when no secondary provider key is configured, not evidence that the policy was missing.

## 5. Rationale for technical decisions

| Decision | Alternative considered | Reason |
|---|---|---|
| **Python + CLI** | FastAPI, Streamlit, WhatsApp | A CLI is sufficient and keeps the evaluation focused on agent behavior. |
| **Single agent with tools** | Multi-agent system / unbounded ReAct | The problem has three well-defined queries; fewer moving parts means fewer failure modes. |
| **Function calling** | A prompt with all the CSVs embedded | The model requests Python functions and receives verifiable results. |
| **HTTPX + OpenAI Chat Completions contract** | A vendor-specific Groq/OpenRouter SDK | Groq and OpenRouter both accept a common HTTP format, making it easy to add other providers. |
| **Groq as primary** | A local model | The project's first experiment already used Groq, and the goal was to ship in 1–2 days. |
| **OpenRouter as optional** | Unlimited retries on the same provider | Lets the 429 fallback path be proven without depending on a single vendor. |
| **CSV via the standard `csv` library** | pandas, PostgreSQL, a SQL agent | Six small tables; `csv` avoids extra infrastructure and dependencies. |
| **Topic-based policy lookup + PDF pages** | Vector-embedding RAG | The manual is eight pages. Selecting relevant pages is simple, auditable, and sufficient for the MVP. |
| **SQLite for conversation history** | Redis/PostgreSQL | Ships with Python, persists context across restarts, and has no external service dependency. |
| **`pytest` + mocks** | Testing exclusively against real APIs | Verifies logic, errors, and fallback reproducibly, with no token cost. |

### How retrieval works

- **Operational data:** `tools.py` re-reads the CSV files at the moment a tool is called. This is a **fictional snapshot**, not a query against a production inventory.
- **Policies:** `policies.py` extracts text from the PDF with `pypdf` and selects pages based on the subject. Every result includes its source page.
- **Prompt:** `agent.py` instructs the model to request data from the tools rather than invent information, to respond courteously, and to ask for human intervention on ambiguous policy questions.

This is **retrieval by source-selection rules**, not semantic RAG with embeddings. That was a deliberate simplicity choice.

### Tool contract

1. `buscar_produtos(nome?, categoria?, preco_max?)`: only offers products that are `active` **and** have `stock_quantity > 0`, with the final price reflecting any active (`is_active=1`) promotion. Results are capped at eight per query.
2. `status_pedido(order_id, email)`: matches the order to the registered email before returning status and tracking; never returns the customer's name, phone, address, or data from other orders.
3. `consultar_politicas(assunto)`: selects pages from the eight-page manual relevant to the question asked.

**Security:** email + order number is a demonstration-only barrier, **not production-grade authentication**. A real system must authenticate the customer through a trusted channel/OTP and enforce access control server-side. The LLM does not decide who is authenticated.

### How fallback works without losing the conversation

1. `history.py` saves the customer's messages to SQLite **before** calling the model.
2. `providers.py` tries Groq first (when configured).
3. On HTTP `429`, `408`, `5xx`, a connection failure, or a timeout, it tries OpenRouter (when configured), sending **the same messages**, including history and any tool results already produced.
4. Whichever API responds continues the conversation. New responses go into the same SQLite history.
5. We do not automatically fall back on HTTP `400`, `401`, or `403`: those errors suggest a configuration, authorization, or invalid-request problem, not a transient overload.
6. If both fail, the system reports the problem and the question stays recorded for a later retry.

**Limits:** we do not transfer hidden internal model state between providers — only the explicit context. There is no guarantee of continuity when both APIs fail. We did not implement a distributed queue, global idempotency, or a cross-process health circuit, because the challenge scope is a local CLI.

The fallback only handles **read-only tools**. For tools that process payments, modify orders, or send real messages, effect idempotency must be implemented before retrying calls.

## 6. Manual rules and ambiguities found

Policy and Procedures Manual, v2.1, June 2025:

- **Hours:** Monday–Friday, 9am–6pm; Saturday, 9am–1pm; Sunday/holidays, closed (p. 2).
- **PIX:** 5% discount on list price, not cumulative with a promotion (pp. 3 and 6).
- **Right of withdrawal:** the manual grants seven calendar days after receipt for online purchases (p. 4). The orders CSV does not contain the **actual receipt date**; the agent must not decide on its own whether the window has closed.
- **Warranty and defects:** the manual mentions a 30-day exchange window (p. 4) and a 90-day legal warranty (p. 7). The agent should reference both rules and refer ambiguous cases onward, without denying rights based on a partial reading.
- **Contact:** the manual lists one phone number in the company's identification section (p. 2) and a different one for WhatsApp support (p. 6). The solution avoids assuming the two are the same.
- **Promotions:** the CSVs have an `is_active` flag but **no start/end dates**. The agent must not assert calendar validity or stack discounts.
- **Stock:** there is a discontinued product with positive stock and an `active` product with zero stock. Both are excluded from availability suggestions.
- **History:** order totals are read from `orders.total_brl`, not recalculated from current product prices.

These ambiguities are documented, not hidden. Artefact's brief allows a reasonable interpretation, provided it is recorded in the README.

## 8. Known limitations / next steps

- The model may **fail to call a tool** even when the prompt calls for it; real scenarios must verify tool calls, and orchestration can be reinforced if it fails. The captured log shows a different failure mode: the tool was called, but the model contradicted the returned products with a false "no results" answer.
- Products, stock, prices, orders, and promotions are **static challenge data**; there is no synchronization with a real store or carrier tracking.
- Keyword-based policy lookup is not equivalent to a robust semantic mechanism. A vector-based RAG with citations would make sense with hundreds of documents, not eight pages.
- Email-based order validation is weak and must not be used in production. The local SQLite also stores messages in plain text; sensitive data would require additional controls in production.
- SQLite stores final messages; intermediate tool steps are replayed in each turn's context but not persisted as independent events.
- Switching between models does not preserve internal state or private reasoning, only explicit history.
- The fallback offers no availability or budget guarantees; the fallback model may have different rates and restrictions.
- There is still no web interface, real human support, strong authentication, centralized observability, or WhatsApp integration.
- The PDF may include a legally questionable rule; this prototype **does not provide legal advice**.

With more time: add semantic evaluation tests (answer fidelity to source), deterministic blocking of unverified outputs, real authentication, edge cases, metrics, data versioning, and deployment as a web API.
